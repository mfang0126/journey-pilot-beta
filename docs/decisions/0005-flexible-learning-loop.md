# 0005：条件化经验、现场交接与持续改进

2026-10-21。方向已由用户明确确认；文档阅读布局是本轮落实方案，不把它表述为用户逐路径指定。本文记录决策与范围，产品概念归 purpose，行为规则归 experience-rules，验收归 requirements，执行进度归 .planning。

## 为什么调整

用户明确要求“我一点都不想把它写死”“不同情况应该具体分析”；认可“交回现场，而不是整道任务重来”和“不只是记步骤，应该是这种条件”。用户要求先反思和落文档，重新 review，再以这些原则分析当前情况，之后才决定下一轮开发。

## 接受的方向

- 保留公共底座＋薄任务脚本；通用方法不等于所有业务都套同一条固定流程。
- 熟路由程序执行，变化由当前 Agent 判断。恢复需要现场、身份和效果核验，不以灵活为由绕过授权、资格或成功条件。
- 经验包括适用与不适用条件，未完成探索也保留认知收益；技术状态仍如实报告。
- 迭代同时改进产品与工作方法，不要求每轮都改框架、改规则或新增文档。
- 日常工作、Research、产品概念、需求思考分开阅读；只加载与本轮有关的材料。

## 落地与权衡

沿用现有仓库与四层归属，不迁移到另一知识库、不复制状态、不搬原始来源。`docs/current-state.md` 组织四个阅读入口；`START-HERE.md` 只负责启动协议。产品概念继续在 `docs/purpose.md`，新增 `docs/user-needs.md` 承载需求和未验证假设；工作循环纳入已有行为规则 §0，Research 仍用 research/README。

这是阅读职责拆分，不为了四个入口机械创建四份副本或大规模改路径。长期规则和历史审查证据分开；旧交接明确标成历史，不能继续覆盖当前计划。

## 对既有计划的限定

0004 中“第二任务不改核心”是那次复用验证的范围，不是所有未来任务的永久禁令。新能力确需共享机制时，可以提出有证据、边界明确的核心改动；不能为了守住一句口号复制机制，也不能凭设想扩框架。

implementation-plan 中固定沉降策略是历史局部实验的候选优化，不是每个页面必须采用的规则。等待机制按页面信号和实测选择，后置条件不变。树、OCR、视觉的使用顺序同样不固化为通用流水线。

R10 明确现场交接的可验收内容；A–D 门槛不降低。候选晋级次数、版本隔离、纯视觉最终成功限制不在本轮放宽范围。

## 本轮范围

只做文档整理、反思、文档 review、源码/既有证据对照分析。此请求不触发新的手机试验、OCR/链接功能开发、安装、模型通道变更、发布、提交或推送。下一实现切片在分析后提出，未因写入建议就自动启动。
