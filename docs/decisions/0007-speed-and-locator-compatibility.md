# 0007：速度优先与配置兼容

日期：2026-10-22。依据：用户要求优先解决 Phone Harness 慢、由助手负责工程决策、尽可能 generic，以简单 key map 兼容，避免每场景重复 Python；随后授权继续开发与现有设备测试。

## 决策

1. 保留单一 Journey 执行循环；页面变化后必须取得新鲜定位依据。移除未验证的 batch/adaptive 分支，明确拒绝其策略字段。不以“两次观察”为硬目标。
2. 已确认同义的控件变化以 `fallback.alternatives` 配置表达，复用同一新鲜树；主定位零命中才试备用项，任一项歧义即暂停。先覆盖 tap/read_field，保持受限动作与 locator 白名单。
3. 现有薄任务保留 Jev 有限选择与结构化交接；通用 Journey 未接入 Jev 备用定位。陌生任务由发起 Agent 基于现场探索、核验，再整理候选配置；不声称自动日志能推导业务语义。
4. 先测耗时与冗余观察/等待，再决定下一项优化。底层显式读树计数与动作墙钟分开；未经同条件实验不承诺比例。
5. 已声明的外部业务写操作在首版 Journey 重放中始终暂停交还 Agent；request.authorization 不作为自动执行开关。
6. 连续验证门槛沿用既有规范。完成率报告实际分子分母及阻塞/介入分类，撤回未经证据支持的“80% 已确认门槛”。

## 实施顺序

修正执行与说明 → 补配置兼容的正常 propose/validate 路径和关键反例 → 同条件真实基线/改造后对照 → 有证据再扩通用参数与学习闭环。自动提炼、双模型仲裁不阻塞提速验证。

不改外部 Phone Harness/Kimi 仓库，不扩大业务写、外发、部署或提交权限。设备锁屏时停止导航测试，不代输凭据。实施顺序见 implementation-plan，状态仅在 .planning，证据在 experiments。
